# ADR-009 — Display-only localization of stored statuses/enums via model-level label maps

## Status

Accepted

---

## Context

SPEC-016 ("Spanish Localization") requires translating the user-facing
presentation to Spanish while leaving all persisted values, business rules and
authorization contracts unchanged. A recurring case is the statuses and enums
stored as fixed English identifiers:

- membership status `pending`/`active`/`expired`/`cancelled`;
- client status `pending`/`active`/`rejected`;
- cuota status `pending`/`paid`/`cancelled`;
- payment status `pending`/`confirmed`/`failed`;
- booking status `confirmed`/`cancelled`;
- turno status `active`/`inactive`/`cancelled`;
- routine status `draft`/`active`/`archived`;
- payment method `cash`/`transfer`;
- exercise muscle-group and difficulty identifiers;
- workout reference type `routine`/`free`.

These identifiers appear in Filament badges (`ucfirst($state)`), filter option
lists, form selects and the client portal Blade views, which today render the
raw English identifier (e.g. "pending", "cash", "active").

The question: where should the Spanish display labels live so they are translated
in presentation only, with a single source of truth, without changing stored
values (BR-003) and without introducing an abstraction the project does not need
(AGENTS.md §20)?

---

## Decision

Centralize each entity's display labels as a **static label map on the owning
model**, keyed by the stored identifier, following the existing
`Exercise::muscleGroupLabels()` / `Exercise::difficultyLabels()` precedent:

- `Exercise::muscleGroupLabels()` / `difficultyLabels()` — translate existing values.
- `Client::statusLabels()`, `Membership::statusLabels()`, `Cuota::statusLabels()`,
  `Payment::statusLabels()`, `Payment::methodLabels()`, `Booking::statusLabels()`,
  `Turno::statusLabels()`, `Routine::statusLabels()`,
  `WorkoutLog::referenceTypeLabels()` — new maps.

Consumers resolve a label with `Model::labels()[($identifier)] ?? $identifier`
(unknown values fall back to the identifier itself, matching the existing
`ExerciseResource::muscleGroupLabel()` behavior). Model constants and database
values remain byte-for-byte unchanged.

The maps live next to the constants they describe, so the identifier set and its
Spanish presentation stay in one place per domain entity. `WorkoutLog::reference_type`
is a transient form/filter toggle (never persisted), but `referenceTypeLabels()`
is still placed on the model to keep the two `WorkoutLogResource` option lists
consistent.

---

## Alternatives

### Alternative A — A shared `App\Support\Labels` helper / registry

A single class mapping every entity's identifiers to Spanish labels.

Rejected: a cross-entity registry duplicates knowledge that already lives on each
model's constants, adds a new abstraction for no concrete benefit, and is not
needed at this scale (AGENTS.md §20).

### Alternative B — A Filament Enum per entity

Replace string constants with Filament's `Filament\Support\Contracts\HasLabel`.

Rejected: would require changing the models' constant representation and all
validation/`in:` rules that depend on the raw string constants — a data/business
change outside SPEC-016's presentation-only scope (BR-002/BR-003).

### Alternative C — Laravel `lang` keys for each status value

Translate through the translator (`trans("statuses.{$value}")`).

Rejected: statuses are fixed domain vocabulary, not user-composed text; the
translator adds indirection and fallback machinery with no benefit over a plain
map, and the maps already follow an established project convention.

### Alternative D — Migrate stored identifiers to Spanish

Rejected: a data/business change that would invalidate constants, validation
rules and existing data (OQ-06; BR-002/BR-003).

---

## Consequences

### Positive

- Single source of truth per entity; identifiers stay the only persisted value.
- Consistent with the existing `Exercise::muscleGroupLabels()` pattern.
- No new abstraction, no dependency, no schema change.
- Each model can carry the gender-appropriate Spanish form for its own entity
  (e.g. membership "Vencida", booking "Cancelada", turno "Cancelado").

### Negative

- Each model must expose (and its tests must cover) one more static map; minor
  duplication of the map shape across models.
- Display labels are coupled to the model layer rather than the view layer; this
  is accepted because the identifiers already live on the models.
