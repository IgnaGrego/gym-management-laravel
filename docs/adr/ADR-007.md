# ADR-007 — CLIENT self-access: ownership-scoped policy/action extensions

## Status

Accepted

---

## Context

SPEC-013 (Client Portal) requires a CLIENT to:

- **view** their own memberships, payments/cuotas, attendance, bookings, assigned
  routine and workout history, plus their own health notes (NC-02);
- **act** on their own data with four self-service actions: book a turno, cancel
  an own booking, log a workout, and edit their own contact fields (NC-01);
- **never** read or mutate another client's data (C-13, BR-002; AGENTS.md §17).

The existing authorization foundation (ADR-001) is purely **role-based**: every
module Policy (Client, Membership, Cuota, Payment, Attendance, Booking,
WorkoutLog, Routine) grants `viewAny`/`view`/`create`/`update` to ADMIN and/or
TRAINER via `User::hasRole`/`hasAnyRole`, and denies CLIENT. There is no
ownership-based access anywhere in the repository yet.

The question: how should CLIENT self-access be integrated with the existing
role-based staff policies, without (a) weakening any staff ability, (b) letting a
CLIENT see or touch another client's records, and (c) introducing a parallel
authorization mechanism that duplicates the per-model policies?

---

## Decision

Use a **two-layer, ownership-scoped extension** of the existing mechanisms:

1. **Instance `view`/`update` abilities are extended with a CLIENT-own term.**
   Each policy's instance methods (`view(User, Model)`, and `update(User, Model)`
   where a client mutation exists) keep their staff clause verbatim and add an
   `||` term that resolves the acting user's linked Client and compares it to the
   model's owning client:

   ```php
   // e.g. BookingPolicy::view / ::update
   return $user->hasAnyRole([Role::ADMIN, Role::TRAINER])
       || ($user->hasRole(Role::CLIENT) && $booking->client_id === $user->clientId());
   ```

   `User::clientId()` is a small helper returning `$this->client?->id` (the
   existing SPEC-002 `hasOne(Client)`). The comparison is the C-13 enforcement.

2. **`viewAny` and class-level `create` stay staff-only.** The portal never
   renders an unrestricted list (its reads are relationship-scoped queries from
   `auth()->user()->client`), and CLIENT self-**create** has no model instance to
   check in a `create(User)` ability. Self-create is enforced where the ownership
   data lives:
   - booking: a self branch in the `CreateBooking` Action (`auth()->user()->client?->id === $clientId`
     → require CLIENT role, persist `booked_by = null`); otherwise the staff
     `Gate::authorize('create', Booking::class)` branch;
   - workout log: the portal endpoint derives `client_id` from the authenticated
     user (never a request field) and is gated by the `role:CLIENT` route;
     `recorded_by = auth()->id()`.

3. **Reads are enforced structurally, not by policy.** Every portal read resolves
   `auth()->user()->client` and queries through that Client's relationships
   (`memberships()`, `attendances()`, `bookings()`, `workoutLogs()`,
   `currentRoutine()`); no request-supplied `client_id` or record id is trusted.
   The extended `view` abilities are the explicit, testable contract and
   defense-in-depth — not the primary read enforcement.

The pattern is documented for the Developer in `docs/architecture/SPEC-013.md`
§5 (Policies), with the exact before/after table for the eight policies.

---

## Alternatives

### Alternative A — A single `PortalPolicy` / `canAccessOwnData` gate

Add one policy (or middleware) that answers "is the acting CLIENT accessing their
own data", and consult it in the portal controllers.

- Pros: one place to change; no per-model policy edits.
- Cons: leaves the eight existing policies inconsistent (they would still deny
  CLIENT, so any future code path using them would silently over- or under-grant);
  duplicates what each policy already expresses per model; the ownership test
  still needs per-model "owning client" knowledge, which is exactly what the
  per-model policies already have.

### Alternative B — Overload `create(User, ?Client $client = null)` for self-create

Widen the standard `create` ability to take an optional target Client, and call
`Gate::authorize('create', [Booking::class, $client])` from the self path.

- Pros: keeps one ability name; the self-ownership check is a policy method.
- Cons: muddies the staff-only admin contract (the same ability now means
  "staff create on behalf" OR "client create for self" depending on arguments);
  requires the non-obvious array-form gate call; the "create for self" semantics
  are clearer as an explicit Action branch where the `booked_by = null` decision
  already lives.

### Alternative C — Dedicated `createForSelf` abilities

Add `BookingPolicy::createForSelf(User, Client)` / `WorkoutLogPolicy::createForSelf(User, Client)`.

- Pros: explicit, directly testable.
- Cons: non-standard ability names for a single call site each; the Action/endpoint
  already has the ownership data at hand, so the ability adds indirection without
  reducing the number of touch points.

---

## Consequences

### Positive

- **No staff ability is weakened** — every staff clause is preserved verbatim;
  the CLIENT-own access is purely additive.
- **C-13 is absolute** — every CLIENT grant is an ownership comparison against
  `auth()->user()->clientId()`; a CLIENT can never pass a foreign record id.
- **One consistent pattern** across all eight policies and the two self-create
  points, replacing ad-hoc per-controller checks.
- **Minimal surface** — only instance `view`/`update` change; `viewAny`/`create`/
  staff `update`/`delete` and all model/action business rules stay untouched.
- **Multi-role correctness** — a staff member who also holds CLIENT gets the
  union (SPEC-001 BR-002): staff abilities via the unchanged clauses, self access
  via the `||` term.

### Negative

- Each policy's ownership comparison loads `auth()->user()->client` (one query
  per check). Irrelevant for the portal (single-record mutation checks;
  relationship-scoped reads), and the `clientId()` helper keeps it cheap.
- `ClientPolicy::update` is broad (CLIENT may update their own Client) while
  `Client` is broadly `fillable`; the field whitelist must be enforced at the
  request layer (`UpdateProfileRequest`), not the policy. A future code path that
  reuses `can('update', $client)` must remember to whitelist fields itself.
- A `RoutinePolicy::view` ownership check must be scoped to the client's
  **current active assignment** (BR-007), which is a slightly more expensive
  `whereHas` than a direct `client_id` compare.
