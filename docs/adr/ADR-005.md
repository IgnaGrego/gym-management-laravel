# ADR-005 — Cuota auto-generation: Membership `created` model hook vs explicit per-path generation

## Status

Accepted

---

## Context

SPEC-005 (Payments & Cuotas) requires that the system auto-generates exactly one
cuota per membership when a membership is created or renewed (FR-001, BR-001,
NC-02), with `amount = plans.price` at generation time (BR-002) and status
`pending` (BR-003). The membership then waits for that single cuota to be paid
before it activates (D-16 option 1; SPEC-004 BR-006).

The existing membership write paths are:

- the Filament `CreateMembership` page (`CreateRecord`, plain Eloquent CRUD);
- the `App\Actions\RenewMembership` Action (wraps `Membership::create()` in a
  `DB::transaction`);

and memberships are also created by tests via `Membership::factory()`.

SPEC-004 explicitly deferred cuota generation to SPEC-005 (SPEC-004 §5 boundary
note, BR-001). Its acceptance criterion AC-18 ("creating a membership does not
create any payment/cuota record") was written under that boundary and is
superseded by SPEC-005 AC-1.

The repository convention is framework-first and model-first (AGENTS.md §10,
ARCHITECTURE §8, §20). The `Membership` model already uses a `booted()`
`creating` hook as the single source of truth for the period invariant
(`end_date`), deliberately covering "the create form, renewal, the factory and
future write paths" (SPEC-004 architecture §5).

The question: where should the one-cuota-per-membership generation live so the
invariant holds across every current and future membership write path?

---

## Decision

Generate the cuota from a `Membership` `created` model event (`booted()`
`static::created` closure), making the model the single source of truth for the
one-cuota-per-membership invariant.

- After a membership is persisted, the hook creates the membership's single
  cuota with `membership_id = $membership->id`, `amount = $membership->plan->price`
  and `status = pending` (BR-001, BR-002, BR-003). Cuota generation never
  modifies the plan, the membership, the client or the user (C-07, BR-010).
- The `cuotas.membership_id` column carries a `UNIQUE` constraint (NC-02), so a
  second cuota for the same membership is rejected by the database as a
  defensive backstop (the event guarantees at most one in practice).
- `RenewMembership` already wraps creation in a `DB::transaction`, so renewal is
  atomic (membership + cuota commit or roll back together). The Filament
  `CreateMembership` page overrides `handleRecordCreation()` to wrap the create
  in a `DB::transaction` as well, matching the renewal precedent and making the
  create path atomic. The `created` event runs synchronously inside whichever
  transaction is active.
- No explicit `CreateCuota` Action and no per-path cuota creation is added; the
  amount edit (FR-002) is a separate, staff-initiated `Cuota::updateAmount()`
  model method, not part of generation.

---

## Alternatives

### Alternative A — Explicit cuota generation in each write path

Create the cuota explicitly in `RenewMembership` and in a `CreateMembership`
page hook (`afterCreate()`/`handleRecordCreation()`).

- Pros: no surprise in tests (a `Membership::factory()` would not create a
  cuota); the generation is visible at each call site.
- Cons: the "system auto-generates one cuota per membership" guarantee is not
  centralized; every future membership write path (e.g., SPEC-007/008
  integration, a bulk import, a new renewal variant) must remember to add the
  cuota, risking memberships without cuotas. This is the exact duplication the
  `booted()` `creating` hook convention was introduced to avoid. Rejected.

### Alternative B — An Eloquent observer (`MembershipObserver`)

Generate the cuota in a dedicated observer class registered in a service
provider.

- Pros: separates the side effect from the model; familiar Laravel pattern.
- Cons: the project does not use observers anywhere; the `booted()` closure
  convention is already established (ADR-004-adjacent, `Membership::booted()`
  `creating` hook). A separate class + registration is an abstraction with no
  concrete benefit here (ARCHITECTURE §7-§9, §20). Rejected.

### Alternative C — Generate on read / no cuota record

Derive the "due amount" from the membership + plan without a persisted cuota.

- Pros: no new table.
- Cons: contradicts SPEC-005 §10 (Cuota is a persistent concept, C-07) and the
  D-02 option 2 requirement that staff may edit a pending cuota amount
  (requires a mutable row). Rejected.

---

## Consequences

### Positive

- The one-cuota-per-membership invariant (NC-02) holds for every write path by
  construction, not by convention; future paths get it automatically.
- Matches the existing `Membership::booted()` hook convention (single source of
  truth) and keeps the create/renew code paths unchanged except for the small
  `CreateMembership` transaction wrap.
- Tests benefit: `$membership->cuota` is always populated, so SPEC-005 tests
  obtain the generated cuota directly instead of constructing it.

### Negative

- `Membership::factory()` now creates a cuota as a side effect; tests that
  create memberships see an extra `cuotas` row. This is harmless for existing
  assertions (they count memberships/clients/plans, not cuotas) but the SPEC-004
  `MembershipManagementTest` case "does not create any payment or cuota record"
  must be updated to assert the new SPEC-005 behavior (AC-1: a cuota IS
  created).
- The `created` event triggers a `plans` read to capture the price; it must run
  inside a transaction to stay atomic, so the `CreateMembership` page gains a
  small transaction wrapper (consistent with `RenewMembership`).
