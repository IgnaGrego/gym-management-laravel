# ADR-001 — Multi-role access model: native pivot vs permission package

## Status

Accepted

---

## Context

SPEC-001 (Authentication & Roles) requires:

- a fixed role catalog of exactly ADMIN, TRAINER, CLIENT (FR-004, BR-001);
- a User may hold one or more roles simultaneously (FR-005, BR-002);
- role checks enforced server-side via Laravel Policies and/or a suitable
  permission mechanism (FR-009, ARCHITECTURE §12);
- no dynamic creation of roles or a granular permission matrix through the UI in
  the MVP (FR-004, out-of-scope §12).

The repository follows AGENTS.md §10 (prefer Laravel mechanisms) and §14 (no
dependency without justification), and ARCHITECTURE §20 (simplest architecture that
correctly represents the domain).

The question: how should roles and role assignment be modeled and checked?

---

## Decision

Use a native relational model with Laravel's built-in mechanisms:

- a `roles` table seeded with the fixed catalog values
  (`Role::ADMIN`, `Role::TRAINER`, `Role::CLIENT` constants on the `Role` model);
- a `role_user` pivot table (composite primary key) linking users to roles;
- Eloquent `belongsToMany` relationships on `User` and `Role`;
- small helpers on `User` (`hasRole`, `hasAnyRole`) for role checks;
- authorization through Laravel Policies, Filament's `canAccessPanel`, and a
  lightweight `EnsureUserHasRole` middleware.

No third-party permission package is installed. The fixed catalog and the absence
of a granular permission matrix in the MVP make a package's main features
unnecessary. The model does not preclude adopting a package later if granular
permissions become a requirement; the normalized roles data would remain valid.

---

## Alternatives

### Alternative A — Spatie Laravel Permission

Install the well-known package: roles, permissions, gates, blade directives,
caching, and Filament integration (e.g., Filament Shield).

- Pros: proven, feature-rich, saves time if a permission matrix is needed later.
- Cons: external dependency (AGENTS.md §14 requires justification); its core value
  (dynamic permissions per role, permission matrix) is explicitly out of MVP scope
  (FR-004); extra tables (`permissions`, `model_has_roles`,
  `role_has_permissions`), caching layer and configuration for a three-role fixed
  catalog.

### Alternative B — Single role column on `users`

Store one role per user in a column or enum.

- Pros: simplest possible schema.
- Cons: violates FR-005 (multi-role users) and BR-002 (union of permissions);
  would require schema redesign later. Rejected.

### Alternative C — JSON array of roles on `users`

Store role names in a JSON column.

- Pros: no pivot table; simple for reads.
- Cons: no referential integrity, no foreign keys, awkward role-scoped queries,
  weaker foundation for later modules' policies. Rejected in favor of a normalized
  pivot, consistent with the modular monolith and Eloquent conventions.

---

## Consequences

### Positive

- No new dependency; the design stays within Laravel conventions (AGENTS.md §10).
- Multi-role users are supported with referential integrity (FR-005).
- The fixed catalog is explicit via `Role` constants and the `RoleSeeder`.
- The foundation is directly consumable by later modules: every module Policy can
  use `$user->hasRole(...)` / `$user->hasAnyRole(...)` (FR-009, AC-12).
- Swapping to a permission package later is feasible without losing role data.

### Negative

- No built-in permission/role management UI (not needed in MVP; `UserResource`
  covers FR-007).
- Role checks require the small helpers on `User` instead of a package API.
- A future granular-permission requirement would need re-evaluation of this ADR.
