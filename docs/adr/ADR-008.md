# ADR-008 — Git branching strategy: main / testing / feature branches

## Status

Accepted

---

## Context

The repository is deployed live (or will be) from the `main` branch. To keep
production stable and enable safe experimentation, the project needs a version
control workflow that prevents breaking the live application.

Without a strategy, work is committed directly to `main`, so any mistake is
instantly live.

The project follows SDD (AGENTS.md): all work goes through Specification →
Architecture → Implementation → Tests → Review before being considered complete.

The question: what git branching model should be used?

---

## Decision

Use a three-tier branching model:

```
feature/*   →   testing   →   main
```

- **`main`** — production-stable. Only receives merges from `testing` via Pull
  Request. Protected: direct pushes are blocked; PR approval is required.
- **`testing`** — integration branch. Receives feature branches, is used for
  testing/deploy-to-staging, and is the source for `main`.
- **`feature/*`** — one branch per task/spec, created from `testing`, merged back
  to `testing` via Pull Request.

Rules:

1. Never commit directly to `main`.
2. Never commit directly to `testing` unless it is a trivial, reviewed change;
   prefer feature branches.
3. A feature branch is created from `testing`, named after the task
   (e.g., `feature/spec-005-payments`).
4. A feature is merged to `testing` via Pull Request.
5. `testing` is merged to `main` via Pull Request only when the integration is
   verified (tests pass, manual QA OK).
6. The default branch on GitHub is `testing` so new Pull Requests target it by
   default.
7. Production deploy comes from `main`.

---

## Alternatives

### Alternative A — Trunk-based (commit directly to `main`)

- Pros: simplest, no merge overhead.
- Cons: every mistake is immediately live; conflicts with a solo-learning workflow
  where experimentation happens frequently. Rejected to protect production.

### Alternative B — GitFlow (main / develop / release / hotfix)

- Pros: industry standard for release management.
- Cons: overkill for a solo portfolio project; `release/*` and `hotfix/*` add
  ceremony without benefit at this stage. `testing` plays the `develop` role with
  a lighter structure.

### Alternative C — GitHub flow only (feature → main)

- Pros: very simple.
- Cons: no place to integrate multiple features before touching production;
  `testing` adds a safe staging step between features and `main`.

---

## Consequences

### Positive

- `main` is always stable; production never receives unreviewed work.
- `testing` is a safe sandbox where features integrate before going live.
- Clear history per feature via Pull Requests (useful for the portfolio).
- Works well with the SDD workflow: one spec → one feature branch → one PR.

### Negative

- Slightly more ceremony than trunk-based (branches + PRs).
- Requires branch protection setup on GitHub (one-time, documented in
  `docs/deploy.md`).
