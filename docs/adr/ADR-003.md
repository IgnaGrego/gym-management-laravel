# ADR-003 — Plan pricing representation: decimal amounts, single implicit currency, validation-level positivity

## Status

Accepted

---

## Context

SPEC-003 (Plan Management) requires:

- a Plan carries a fixed price per period plus an optional one-time enrollment fee
  (matrícula) (BR-001, D-14 Recommended option 2, assumption AP-01);
- the price must be a positive amount; the enrollment fee, when present, must be
  zero or a positive amount (BR-002);
- monetary amounts are stored as plain numeric amounts in the MVP's single
  implicit currency; the exact column precision is an Architect decision
  (SPEC-003 §10, AP-05, OQ-07);
- Plan, Membership and Payment are separate, persistent concepts (C-07,
  ARCHITECTURE §14); SPEC-004 (Memberships) and SPEC-005 (Payments & Cuotas) will
  consume the plan price.

The repository follows AGENTS.md §10 (prefer Laravel mechanisms), §14 (no
dependency without justification), and ARCHITECTURE §20 (simplest architecture that
correctly represents the domain).

The question: how should monetary amounts on a Plan be represented in the database
and validated?

---

## Decision

### 1. Monetary columns are `decimal(10, 2)` with Eloquent `decimal:2` casts

- `plans.price` — `decimal(10, 2)`, NOT NULL.
- `plans.enrollment_fee` — `decimal(10, 2)`, nullable (`null` when absent, not 0).
- The `Plan` model casts both to `decimal:2`.
- `decimal(10,2)` supports amounts up to 99,999,999.99 — far beyond any MVP plan
  price — and matches Laravel's first-class decimal support.

### 2. No currency column: a single implicit currency

- The MVP uses one implicit currency (context suggests ARS); no `currency` column
  is added (AP-05). This part is an **unconfirmed assumption** and requires PO
  confirmation (OQ-07); a `currency` column can be added additively later.

### 3. Positivity is enforced by framework validation, not DB constraints

- BR-002 (price > 0, fee >= 0) is enforced by the Filament form validation rules
  (`numeric`, `min:0.01` for price; `nullable`, `numeric`, `min:0` for the fee).
- No PostgreSQL CHECK constraints are added in the migration. This is consistent
  with the project convention: all write paths go through the Filament form and no
  existing migration uses raw SQL constraints (AGENTS.md §10). If a non-validated
  write path ever appears, an optional CHECK constraint
  (`price > 0`, `enrollment_fee >= 0`) is the documented hardening.

### 4. No price-history or versioning table

- Plan versioning / price history is explicitly out of scope (SPEC-003 §12); the
  question of how price edits affect existing memberships belongs to SPEC-004
  (OQ-06). No history mechanism is introduced now.

---

## Alternatives

### Alternative A — Integer cents (minor units)

Store amounts as integers (e.g., `price_cents`).

- Pros: exact arithmetic, no decimal-string handling.
- Cons: conversion layer everywhere (forms, display, casts), not a documented
  project pattern, and Laravel's `decimal` support already handles the two-decimal
  case cleanly. Rejected.

### Alternative B — DB CHECK constraints on amounts

Add `CHECK (price > 0)` and `CHECK (enrollment_fee >= 0)` in the migration.

- Pros: the database itself rejects invalid amounts even on non-validated write
  paths.
- Cons: raw SQL in migrations (Laravel has no native check-constraint helper),
  inconsistent with the framework-validation-first convention and the existing
  migrations. Rejected for the MVP; kept as documented optional hardening.

### Alternative C — Currency column now

Add `currency` (e.g., default `ARS`) to `plans`.

- Pros: future-proof if the gym ever prices in multiple currencies.
- Cons: speculative — the domain explicitly assumes a single implicit currency
  (AP-05, OQ-07) and ARCHITECTURE §20 favors the simplest correct design. A
  `currency` column can be added additively later without data migration of
  amounts. Rejected for now.

### Alternative D — Money as float/double

- Pros: simplest Laravel syntax.
- Cons: binary floating-point representation errors on financial amounts. Rejected;
  `decimal` is the correct PostgreSQL type for money.

---

## Consequences

### Positive

- Simple and idiomatic Laravel: `decimal(10,2)` columns, `decimal:2` casts,
  `numeric` validation rules (ARCHITECTURE §20).
- The precision supports any realistic MVP plan price and is trivially changeable
  by migration if the PO confirms a different precision (OQ-07).
- SPEC-004/SPEC-005 can read `plans.price` / `plans.enrollment_fee` as plain
  decimal amounts without conversion, keeping the Plan/Membership/Payment
  separation clean (C-07).
- No new dependency and no raw SQL in migrations.

### Negative

- Eloquent `decimal:2` casts return strings; developers must format display
  columns and use `numeric` rules consistently (risk documented in
  `docs/architecture/SPEC-003.md` §9).
- The single-implicit-currency assumption (AP-05) is unconfirmed; if the PO later
  requires multi-currency, a `currency` column must be added (additive migration).
- No DB-level guard against invalid amounts; enforcement relies on the form
  validation path (mitigated because all MVP write paths use the Filament form).
