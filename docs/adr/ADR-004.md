# ADR-004 — Membership expiry materialization: scheduled command vs computed on read

## Status

Accepted

---

## Context

SPEC-004 (Membership Management) requires:

- a membership has exactly four states: `pending`, `active`, `expired`,
  `cancelled` (BR-004, assumption AM-03);
- a membership whose end date has passed is never considered active or usable;
  it is `expired` (BR-007, AM-10). The `expired` state applies to both
  `pending` (never paid) and `active` memberships whose period ended;
- `expired` is terminal in the MVP: no reactivation, extension or reopening
  (BR-009, AM-10);
- whether the `expired` status is materialized by a scheduled job or computed
  on read is explicitly delegated to the Architect (BR-007; acceptance
  criterion AC-12: "A membership whose end date has passed is never reported
  `active` (BR-007, AM-10); the mechanism (scheduled job vs. computed on read)
  is verified per the Architect's design");
- the status must be consumable by later Specifications: SPEC-005 (Payments &
  Cuotas) generates cuotas per membership and triggers `pending → active`;
  SPEC-007 (Bookings) and SPEC-008 (Attendance) consume membership state under
  the access rule D-05 (SPEC-004 §12, BR-016). FR-002 requires listing and
  filtering memberships by status.

The repository follows AGENTS.md §10 (prefer Laravel mechanisms), §12
(database), and ARCHITECTURE §20 (simplest architecture that correctly
represents the domain), and the SPEC-001/002/003 precedent of framework-first
validation and stored state (e.g., `users.is_active`, `plans.is_active`,
`plans.is_active` toggles) rather than derived values.

The question: how should the `expired` state be represented and kept accurate?

---

## Decision

Materialize the `expired` state in the `memberships.status` column via a
daily scheduled console command, and keep `status` as the single source of
truth for queries.

- New command `memberships:expire` (`App\Console\Commands\ExpireMemberships`):
  idempotently sets `status = 'expired'` on all memberships where `status` is
  `pending` or `active` AND `end_date < today()` (BR-007). The command updates
  only the status column; it does not touch period fields or related records
  (BR-011, BR-013).
- Registered in `routes/console.php` (Laravel 11 convention, already used by
  the scaffold): `Schedule::command('memberships:expire')->dailyAt('00:05');`
  (the exact early-morning time is an ops choice; it minimizes the window
  between midnight and the materialization while the gym is closed).
- The membership model exposes `Membership::activate()` which additionally
  guards "only while within the validity period" (AC-15): a `pending`
  membership whose end date has passed cannot be activated even in the window
  before the next command run. This closes the staleness gap for the only
  state transition that depends on the period (FR-008).
- All consumers (FR-002 status filters, SPEC-005, SPEC-007/008) query the
  stored `status` column directly; no consumer recomputes "effective expired"
  from dates.
- Deployment requires the Laravel scheduler to run (cron
  `php artisan schedule:run` every minute, or equivalent in the Docker
  setup), which is documented in the architecture document and the ops notes.

---

## Alternatives

### Alternative A — Computed on read

Do not store `expired`; treat a `pending`/`active` membership whose `end_date`
has passed as `expired` through an accessor / query scope at read time.

- Pros: always current, no scheduler dependency, no staleness window.
- Cons: the stored status column no longer reflects the business state; every
  status query must add date conditions (FR-002 status filtering, SPEC-005
  cuota generation, SPEC-007/008 access rules would each re-derive the
  effective status); the four-state machine becomes partially derived, which
  complicates the policy/consumer contract and increases the risk of
  inconsistent implementations across modules in the modular monolith.
  Rejected.

### Alternative B — Database-level computed column / view

Represent `expired` via a generated column or a DB view.

- Pros: DB enforces correctness.
- Cons: raw SQL and Postgres-specific DDL, inconsistent with the project's
  validation-first, framework-first convention (ADR-003 rejected DB CHECK
  constraints for the same reason); harder to evolve when the PO confirms
  AM-10 or adds freeze states later; over-engineering for a day-granular
  business rule. Rejected.

### Alternative C — Queued job (Laravel queue worker)

Dispatch a queued job instead of a scheduled console command.

- Pros: uses the existing Redis/queue infrastructure (ARCHITECTURE §11).
- Cons: the operation is a fast, idempotent bulk UPDATE that does not need
  queue semantics (retries, workers, backpressure); a queued job adds moving
  parts without benefit (ARCHITECTURE §11: "Do not queue operations that need
  immediate consistency"). A scheduled command is the simplest Laravel
  mechanism. Rejected.

---

## Consequences

### Positive

- `memberships.status` is the authoritative four-state value; FR-002 status
  filters and future consumers query a plain column with no derived logic.
- The command is idempotent and trivial to test (AC-12 verified by running the
  command in tests).
- Consistent with the project's stored-state precedent (`is_active` flags) and
  its framework-first convention.
- The period guard in `activate()` ensures a membership is never activated
  after its end date even in the window before the next command run (AC-15).

### Negative

- Requires the Laravel scheduler to be running in every environment; if it is
  not deployed, `expired` materialization stalls (mitigated by the
  `activate()` period guard and by the day-granular nature of the rule).
- Small staleness window between midnight and the scheduled run: a membership
  whose end date passed at 00:00 is reported `active` until the command runs
  (00:05 by default). This is operationally irrelevant for a gym and bounded
  to minutes.
- Adding a future state (e.g., `frozen`) still requires touching the command
  and constants, but that is true of any state-machine design.
