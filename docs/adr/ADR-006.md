# ADR-006 — Atomic capacity enforcement for bookings: pessimistic row lock on the turno

## Status

Accepted

---

## Context

SPEC-007 (Bookings) requires capacity enforcement on turnos (D-07 option 1;
SPEC-006 FR-009 deferred):

- a booking can be created only if the number of `confirmed` bookings for the
  turno is strictly less than the turno's `capacity_limit` (BR-008);
- the capacity check and the booking insert must be **atomic**: when two
  booking attempts race for the last spot, exactly one succeeds and the other
  is rejected as "turno full"; overselling is never allowed (BR-008, ERR-011,
  AC-9);
- a client can have at most one `confirmed` booking per (client, turno)
  (BR-009, ERR-008);
- `cancelled` bookings do not count toward capacity (BK-11).

This is the first concurrency-control requirement in the repository: every
prior Specification (SPEC-001..006, 008..012, 015) is effectively single-writer
CRUD or single-record state transitions, so a "count then insert" check is
sufficient there. For bookings, a naive `count()` in form validation followed
by an `insert` is subject to a time-of-check/time-of-use (TOCTOU) race: two
concurrent transactions can both observe "one spot left" and both insert,
overselling the turno.

The enforcement mechanism is explicitly delegated to the Architect (SPEC-007
BR-008: "the enforcement mechanism ... is an Architect decision").

---

## Decision

Enforce capacity inside the `CreateBooking` Action using a database transaction
with a **pessimistic row lock on the turno row**, plus a **partial unique index**
as the hard guarantee for the duplicate invariant.

1. **Transaction + `SELECT ... FOR UPDATE` on the turno.** Within
   `DB::transaction()`, the Action first loads the turno with
   `Turno::query()->lockForUpdate()->findOrFail($turnoId)`. This takes a
   row-level exclusive lock on the turno for the duration of the transaction.
   Because every booking insert for a given turno first locks the same turno
   row, concurrent booking attempts for that turno serialize: the second
   transaction blocks on the lock until the first commits, then reads the
   committed count. The Action then:
   - counts `confirmed` bookings for the turno (`Booking::confirmedCountForTurno()`);
   - throws "turno full" if `count >= capacity_limit` (ERR-007, ERR-011);
   - re-checks the duplicate invariant and throws if a `confirmed` booking
     already exists for the same `(client_id, turno_id)` (ERR-008, BR-009);
   - inserts the booking with `status = 'confirmed'`.
   Exactly one concurrent attempt wins the last spot; the other is rejected.

2. **Partial unique index for BR-009.** The migration creates:
   `CREATE UNIQUE INDEX bookings_confirmed_client_turno_unique ON bookings
   (client_id, turno_id) WHERE status = 'confirmed'`. This enforces "at most
   one `confirmed` booking per (client, turno)" at the database level and is
   the backstop for any write path that bypasses the Action, while still
   allowing any number of `cancelled` rows for the same pair (AF-003). This is
   the single intentional raw-SQL statement in the migration: Laravel's schema
   builder has no partial-index API and PostgreSQL supports partial indexes
   natively.

3. **Non-atomic rules stay in framework validation.** The access gate (D-05
   option 1), turno `active` state and turno time-validity/lead-time are
   checked in the Action's `validate()` step before the transaction (they do
   not need atomicity); the capacity + duplicate checks are re-evaluated
   *inside* the lock because only they are race-sensitive.

The default PostgreSQL isolation level (READ COMMITTED) is sufficient: the
explicit `FOR UPDATE` lock, not the isolation level, provides the serialization
of concurrent writers on the same turno row.

---

## Alternatives

### Alternative A — Form-level count check (no transaction, no lock)

Count confirmed bookings in a Filament form rule, then let the resource insert.

- Pros: matches the `AttendanceResource` gate-rule style; no new infrastructure.
- Cons: TOCTOU race — the check and insert are separate statements, so
  concurrent attempts can both pass and oversell (violates BR-008, ERR-011,
  AC-9). Rejected: the spec's atomicity requirement is explicit.

### Alternative B — PostgreSQL advisory lock (`pg_advisory_xact_lock`)

Take `pg_advisory_xact_lock(turno_id)` at the start of the transaction.

- Pros: works without needing a turno row to lock; explicit and cheap.
- Cons: bypasses Eloquent with an opaque lock identifier; requires a
  lock-namespace discipline (risk of collision with future advisory-lock uses);
  harder to read. The turno row always exists, so a row lock is simpler and
  self-documenting. Rejected in favor of the row lock.

### Alternative C — Database-level guard (CHECK + counting function, or a
capacity "slot" table)

Enforce the invariant with a trigger/constraint that counts confirmed bookings,
or model each spot as a row.

- Pros: strongest DB guarantee, no application-lock discipline.
- Cons: raw SQL / complex DDL and Postgres-specific code, contrary to the
  project's validation-first, framework-first convention (ADR-003 rejected DB
  CHECK constraints for the same reason); a slot table would be a large
  restructuring for a day-granular rule. Rejected as over-engineering.

### Alternative D — Optimistic concurrency / retry loop

Attempt the insert and retry on a unique/conflict violation.

- Pros: lock-free under low contention.
- Cons: capacity has no unique constraint to key a conflict on (only the
  `(client, turno)` duplicate does); a retry loop on capacity would be fragile
  and non-deterministic. Rejected.

---

## Consequences

### Positive

- Correctness under concurrency: overselling is impossible; exactly one
  concurrent attempt wins the last spot (AC-9).
- Simple and idiomatic: `lockForUpdate()` is standard Laravel and the lock
  protects the existing turno row — no new lock infrastructure.
- Portable across PostgreSQL and MySQL (the two databases Laravel commonly
  targets here), and the partial unique index has a clear Postgres fallback if
  portability is ever required (a full unique + check, or a nullable
  `cancelled_at` column).
- The capacity and duplicate checks are self-documenting inside the Action, and
  the Action is directly testable for the race (driven with two transactions).
- The partial unique index enforces BR-009 even for non-Action write paths.

### Negative

- Pessimistic locking serializes concurrent bookings for the *same* turno:
  later requests block until the current transaction commits. The lock is held
  for a very short single-insert transaction, and gym-scale booking traffic
  (a handful of slots per turno, staff-driven in the MVP) makes this
  negligible.
- The capacity check can no longer live in a plain Filament form rule; it must
  live in the Action (the form may still surface the error message). This is a
  deliberate placement change and is documented in the SPEC-007 architecture.
- One raw-SQL statement (the partial index) is introduced; it is isolated,
  documented, and covered by a unit test asserting the BR-009 violation.
