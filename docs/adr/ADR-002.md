# ADR-002 — Client record data model: standalone `clients` table, nullable unique user link, in-table health columns

## Status

Accepted

---

## Context

SPEC-002 (Client Management) requires:

- client records are standalone; a linked User account is optional and can be
  created later (PO-confirmed decision D-01 / SPEC-001 assumption A-01);
- a Client links to at most one User account, and a linked account belongs to
  exactly one Client — a 1:1 link (BR-003), established only by explicit
  provisioning (FR-005, BR-002);
- health notes (emergency contact, injuries, medical conditions) are sensitive
  data; the access restriction is the business rule (BR-007);
- client records are never hard-deleted (BR-006).

The Specification explicitly delegates one schema decision to the Architect:
"the health data separation (separate table vs. clearly separated fields) is an
Architect decision" (SPEC-002 §10). The location and shape of the Client ↔ User
link is also an Architect decision; the Specification only states the business
rule (BR-003).

The repository follows AGENTS.md §10 (prefer Laravel mechanisms) and
ARCHITECTURE §20 (simplest architecture that correctly represents the domain),
and the SPEC-001 foundation already implements the `users`, `roles` and
`role_user` tables.

Two questions must be decided:

1. Where is the Client ↔ User link stored?
2. Are health fields stored in the `clients` table or in a separate table?

---

## Decision

### 1. Link direction: `clients.user_id`

Add a new `clients` table with a **nullable, unique foreign key `user_id`**
pointing to `users.id`, with `nullOnDelete`.

- The unique index enforces BR-003 in both directions: at most one linked User
  per Client (a client row can hold only one `user_id`) and at most one Client
  per linked User (no two client rows may reference the same user).
- `users` is untouched: no new column on the completed SPEC-001 foundation.
- The link is written only by the explicit provisioning Action
  (`App\Actions\ProvisionClientUser`), never by client create/edit (BR-002).
- `nullOnDelete` is a defensive safety net: users are never hard-deleted in the
  MVP (SPEC-001 BR-007), and if a linked User were ever removed, the Client
  record must survive (BR-008).

### 2. Health data: clearly separated columns in `clients`

Store `emergency_contact` (string), `injuries_notes` (text) and
`medical_conditions_notes` (text) as nullable columns of `clients`, separated
from identity/contact columns.

- The access restriction (BR-007) is enforced by `ClientPolicy` (ADMIN-only in
  this Specification) plus UI discipline: health fields never appear in lists
  or search results, only in the client detail view and the management forms.
- If future rules change access granularity (e.g., OQ-02 grants TRAINER access
  to non-health data, or OQ-01 requires a consent record), the columns can be
  moved to a 1:1 health/consent table or guarded by a policy split without
  losing data.

---

## Alternatives

### Alternative A — Link stored as `users.client_id`

Add a nullable unique `client_id` column to the `users` table.

- Pros: the link lives with the authenticated identity; querying a user's
  client is a local column read.
- Cons: couples the completed SPEC-001 authentication foundation with a
  business module; every user record carries a client slot; the existing
  `UserResource` user-management flow and `User` model would need changes;
  provisioning would modify the Users module rather than the Clients module.
  Rejected.

### Alternative B — Separate `client_user` link table

A dedicated pivot-like table with `client_id` and `user_id` (both unique).

- Pros: explicit; could host future link metadata (e.g., link date, unlink
  history for OQ-06).
- Cons: over-engineering for a nullable 1:1 link; extra table, join and
  integrity management with no functional benefit over a unique FK. Rejected.

### Alternative C — Separate `client_health_data` table (1:1)

Move health fields into their own table with a foreign key to `clients`.

- Pros: physical separation of sensitive data; a natural place for future
  consent records (OQ-01); makes a future TRAINER non-health access split
  (OQ-02) structurally explicit.
- Cons: today the whole module is ADMIN-only, so a second table adds
  complexity (extra model, relationship, form/infolist wiring, joins) with no
  additional protection — the access restriction is already enforced by the
  module-level policy. Rejected for the MVP; the in-table separated columns
  preserve the migration path.

---

## Consequences

### Positive

- The SPEC-001 `users` schema and user-management flow remain untouched; the
  Clients module is self-contained and greenfield.
- BR-003 (1:1 link) is enforced by the database itself via the unique index,
  not only by application logic.
- Health data restriction is enforced at the single policy touch point and by
  UI discipline; no redundant table for a rule that is module-wide today.
- Standard Eloquent CRUD with no repositories or extra abstractions
  (ARCHITECTURE §9).
- Future consent records (OQ-01) and TRAINER access splits (OQ-02) remain
  feasible without data loss.

### Negative

- If the PO later decides that TRAINER (or CLIENT self-service) may see
  non-health client data, the in-table health columns require either a
  policy-level field split or a migration to a separate health table.
- The `clients.user_id` FK direction means "user has a client" is read through
  `User::client()` (HasOne via `clients.user_id`), which is slightly less
  direct than a column on `users` but keeps module boundaries clean.
